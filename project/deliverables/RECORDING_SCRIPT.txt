Hi, I'm Tal Berkovitch, and this is my project for the course "AI in

It's a multi-agent AI Security Operations Center that detects DNS-based attacks

------------------------------------------------------------------------------
SEGMENT 2 — THE PIPELINE  (slide "1")                              (~55 sec)
------------------------------------------------------------------------------
First, the big picture — capture, detect, explain, stream.

On the left, in the red box, is the air-gapped detonation plane. Three
containers on an internal-only Docker network with no route to the internet.
The Attacker generates realistic benign DNS traffic plus three attack injectors.
The Collector is the DNS resolver where traffic terminates — and it hosts a
passive packet tap. And the Defender is the brain: it captures packets, extracts
features, runs the detector, and raises alerts.

[ point to the purple box on the right ]
On the right is the egress SOC zone — off the air-gapped network. I used kafka to carry the data out to where a CTI worker turns alerts into reports.
and a live dashboard streams everything to the analyst.

The three ideas to hold onto: we detect by behaviour, not signatures — the model
learns the normal DNS heartbeat with no attack labels. The detector is pluggable.
And we don't just detect, we explain.

------------------------------------------------------------------------------
SEGMENT 3 — THE MODEL  (slide "2")                                (~60 sec)
------------------------------------------------------------------------------
Now the deep-learning model — and this is the most interesting result.

My first version, on the left, was a plain autoencoder over aggregate window
features — things like query rate and entropy. An autoencoder learns to
reconstruct normal traffic, so anything it reconstructs badly is an anomaly. The
problem: by summarizing each window into a feature vector, it throws away the
query name text itself — which is the most discriminating signal.

We evaluate with ROC-AUC — Receiver Operating Characteristic,  Area Under the Curve — a metric that measures how often the model gives attacks a higher anomaly score than benign queries.

The plain autoencoder topped out around 0.91 for our evaluation metric.

So version two, on the right, is a character-embedding autoencoder. It
reads each query name character by character — embedding, GRU encoder, a latent
bottleneck, GRU decoder — and learns the lexical shape of benign names. When an
attacker encodes stolen data into a query name, you get long, high-entropy
base32 strings that reconstruct badly and light up immediately.

[ point to the green strip ]
And here's the key finding: same data, same anomaly idea — the only thing that
changed is the input representation. Going from window features to per-character
sequence lifted held-out exfiltration from 0.91 to a perfect 1.000. The
representation mattered more than the algorithm.

------------------------------------------------------------------------------
SEGMENT 4 — TWO DETECTORS  (slide "3")                            (~45 sec)
------------------------------------------------------------------------------
I actually run two detectors, because they cover each other's blind spots.

The character-embedding autoencoder is lexical — it scores the text of each
query, and it's unbeatable on high-entropy encoded names.

The Isolation Forest is behavioural — it scores per-window features like query
rate, subdomain entropy, and NXDOMAIN rate. That catches the sneaky stuff: word-
encoded, low-and-slow payloads that the lexical model is, by design, blind to.

Both sit behind one pluggable interface. So with a single flag I can swap between
the CPU autoencoder, the Isolation Forest, or an NVIDIA Morpheus GPU backend —
with no change anywhere downstream. That's the Morpheus plug-and-play design the
course is built around.

------------------------------------------------------------------------------
SEGMENT 5 — HOW THE CTI WORKS  (slide "4")                        (~50 sec)
------------------------------------------------------------------------------
Detecting is only half of it. An analyst needs to know what it means — so every
alert becomes a piece of threat intelligence.

The flow goes left to right. We start with the alert and its per-feature attribution — which features drove the score. We use those features to retrieve the matching MITRE ATT&CK technique cards from a curated DNS knowledge base — a lightweight keyword match, no embeddings needed. Then we augment the LLM's prompt with those retrieved cards, and the multi-agent chat generates the report grounded only in them — that's the "retrieval-augmented generation," the RAG step. And out comes a structured SOC report: summary, evidence, MITRE IDs, severity, and recommended actions.

The important part: this is grounded, not free-form. The language model only
confirms and writes up techniques the retrieval already surfaced — it never
invents IPs or numbers. And if there's no API key, a deterministic template
takes over, so it always runs.

Across all three attack types — tunneling, exfiltration, and C2 — we get the
correct MITRE technique in the top three, every single time.

------------------------------------------------------------------------------
SEGMENT 6 — MULTI-AGENT ORCHESTRATION  (slide "5")                (~50 sec)
------------------------------------------------------------------------------
So what actually makes this multi-agent? Let me be concrete about the agents and
the LLM calls.

There are two LLM agents in a bounded group chat. The Threat-Analyst takes the
anomaly score, the attribution, and the retrieved ATT&CK cards as its inputs, and
decides which techniques the evidence supports and how severe it is. The
Report-Writer takes that assessment and writes the final report, then signals
TERMINATE. A third agent, the Evidence proxy, makes no LLM calls at all — it just
seeds the conversation and runs the round-robin, capped at four rounds.

[ point to the right panel ]
On the right are the LLM invocations themselves. One per alert for the CTI report.
A periodic one for the dashboard's live situation summary. And an on-demand one to
switch the model live.

And it degrades gracefully — the chat is bounded, throttled, and never a hard
dependency. If the key is missing or anything errors, it falls back to a
deterministic report. The air-gapped defender, by the way, never calls an LLM.

------------------------------------------------------------------------------
SEGMENT 7 — THE STACK  (slide "6")                                (~35 sec)
------------------------------------------------------------------------------
Quickly, the main tools and what each one does.

Docker gives us the isolated, internal-only detonation plane — that's the air-gap.
Apache Kafka is the transport spine carrying data between zones. PyTorch runs the
character-embedding autoencoder; scikit-learn runs the Isolation Forest. AG2 —
AutoGen — orchestrates the multi-agent chat, and Groq serves the LLM behind it.
FastAPI with Server-Sent Events powers the live dashboard. And NVIDIA Morpheus is
the plug-and-play GPU backend behind that same detector interface.

------------------------------------------------------------------------------
SEGMENT 8 — RESULTS  (slide "7")                                  (~35 sec)
------------------------------------------------------------------------------
To wrap the results: a perfect ROC-AUC, recall of one at a tenth-of-a-percent
false-positive rate, correct MITRE mapping in the top three every time, and zero
internet routes out of the attack plane.

The headline takeaway is that the representation beat the algorithm, and that
detection and explanation are driven by the same evidence. Future work is running
the Morpheus GPU backend for a throughput comparison and extending to more covert
channels.
